# 00_policy.md - 開発方針

## 1. 目的と対象

本書は、閉域または庁内ネットワークで職員が使う小規模な内部業務支援ツールの恒久的な開発ガードレールである。JavaScript、PowerShell、C# を主な対象とし、基幹システム、公式記録の管理、法令・最終業務判断の代替は対象外とする。

`lg_toolkit_guide` はガイド、テンプレート、プロンプトを管理する。再利用可能なコード部品は [`lg_toolkit`](https://github.com/YanTKYS/lg_toolkit) で管理し、本リポジトリに `common/` や共通ライブラリを設けない。個別ツール本体は個別リポジトリで管理する。

## 2. ガイドとプロンプトの役割

- ガイドには、案件をまたいで守る方針、品質基準、確認観点を置く。
- 個別プロンプトには、案件固有の目的、対象、要件、制約、今回の作業だけを書く。
- 閉域、外部依存、README構成、標準成果物など、参照するガイドの内容をプロンプトへ長く再掲しない。
- 実開発で不足した恒久ルールは、次のプロンプトを長くするのではなくガイドへ戻す。
- URL参照ができない場合は `exports/guide_context.md` を `reference/guide_context.md` として同梱する。

## 3. 基本方針

1. 閉域で再現でき、外部通信、外部API、CDN、クラウドを前提にしない。
2. 追加インストール、管理者権限、複雑なビルド環境を当然の前提にしない。
3. 個人情報を外部送信せず、保存・ログ出力を必要最小限にする。
4. 元データを保護し、確認なしの上書き・削除を避ける。
5. 出力は補助情報とし、利用者または所管部署が確認して最終判断する。
6. 流行や技術的な立派さより、運用容易性、説明容易性、保守性を優先する。

外部ライブラリが本当に必要な場合は、ライセンス、採用理由、固定バージョン、ローカル同梱方法、更新方法を記録する。

## 4. 作業の完結性

依頼範囲は可能な限り、**調査 → 実施 → 確認 → テスト → ドキュメント整合 → 報告**まで一気通貫で完了する。調査、設計、TODO作成だけで実施可能な後続作業を先送りしない。

実機や権限などの理由で確認できない項目は推測で合格にせず、次を記録する。

- 未確認項目と理由
- 想定リスク・影響範囲
- 次の確認手順、担当、必要なら期限

## 5. 技術的試行と小規模ツール

- PoCでは最終目的、守る制約、避ける逸脱をガードレールとして示し、細かな手順を固定しすぎない。
- 中間成果を目的化せず、利用者が一連の操作を試せる状態まで進める。
- 小規模ツールに、大規模アプリ向けの抽象化、細分化、設定ファイル、共通基盤を安易に導入しない。
- 将来拡張性は、現在の利用目的と理解しやすさを阻害しない範囲で考慮する。

## 6. UI/UX

目的は、一般職員が迷わず使えることである。次の順で減らす。

1. 利用者が見る情報量
2. 利用者が判断する回数
3. 操作の手数
4. 操作時の迷い

既存機能へ自然に接続できる場合は、新画面、設定、説明、モードの追加より統合を優先する。画面構成、カード、ボタン数、文字サイズなどは参考例であり、絶対条件ではない。詳細は `guides/04_ui_ux_rules.md` を参照する。

## 7. 共通化・リファクタリング

共通化は先に設計せず、実際の重複から抽出する。簡素化は原則として次の順で検討する。

1. 不要な処理を削除する
2. 既存コードを再利用する
3. 標準API・標準機能へ置き換える
4. 導入済みライブラリを利用する
5. 単純な実装で済ませる
6. 必要性が明確な場合だけ独自共通コードを作る

明確な利点のない新規依存や車輪の再発明を避ける。リファクタリングは重複、バグ、保守負荷、可読性などの具体的な理由がある場合だけ行う。

## 8. バグ修正とテスト

通常業務を妨げる計算ミス、フリーズ、予期しない終了、データ破損、操作不能、誤表示を優先して直す。通常発生しない極端な桁数、特殊な文字列、非現実的な入力だけのために実装を複雑化しない。

テストは正常系、現実的な異常系、境界値、再実行、回帰を優先する。ファイル処理では元データ保護と失敗後の復旧も確認する。

## 9. READMEと既知の制限

READMEは「現在このツールを使う人が必要な情報」を示す現行仕様書とする。概要、対象利用者、利用環境、現在できること、操作、入出力、安全上の注意、保守・問い合わせ先、確認方法を中心にする。

- 更新履歴はREADMEへ積み上げず、必要なら release notes やGit履歴へ分離する。
- 非対応事項を網羅しない。対象外や制約は、利用者が実際に判断するために必要なものだけ記載する。
- 既知の制限は利用者・保守者に有用なものに限る。
- 解消可能で通常利用を妨げる問題は、制限として残すより修正を優先する。

## 10. 安定版とリリース

安定したツールでは機能追加を目的化せず、回帰確認、データ保護、文書整合、配布・起動確認を優先する。総点検で問題が再現しなければ、無理にコードを変更せず確認記録だけで完了してよい。

配布物を持つツールでは、必要に応じて `guides/14_github_actions_build_release.md` を使う。GitHub Actions / Releaseは全ツール必須ではない。

## 11. AIによる設計逸脱

第三者AIレビュー、変更申請、判断ログの方針は `guides/13_policy_deviation_review.md` に従う。実装AIの反論を一律に拒否せず、次のどれかを見極め、最終判断はユーザーが行う。

- ユーザーの考慮不足を補っている
- 一般論・過剰設計へ逸脱している
- 実装しやすい方向へ逃げている

## 12. 成果物と報告

成果物は案件の規模、段階、配布・引継ぎの必要性に応じて選ぶ。代表例は `README.md`、実装、設計・テスト・引継ぎ文書、利用者別手順書、`development_report.md` である。すべてを機械的に必須とせず、必要な文書は既存テンプレートを使う。

作業後は変更内容、実施した確認・テスト、文書整合、未確認事項、あえて変更しなかったものを報告する。実際の差分と報告内容を一致させる。
