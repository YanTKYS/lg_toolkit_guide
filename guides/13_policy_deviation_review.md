# 13_policy_deviation_review.md - 方針逸脱レビューガイド

## 1. 目的

このガイドは、Vibe Codingにおいて実装AIがユーザー方針や設計思想から逸脱する提案をした場合に、その逸脱が妥当かどうかを審査するための基準です。

- 実装AIの反論や設計変更提案を、感覚的に採用・却下しない。
- ユーザーの考慮不足を補う有益な反論と、過剰設計・一般論・逃げの逸脱を分ける。
- 最終決定権はユーザーに残しつつ、判断材料を整理する。
- 判断ログを残して、後から振り返れるようにする。

## 2. 基本方針

- 最終決定権はユーザーにある。
- ただし、ユーザーの設計が常に正しいとは限らない。
- 実装AIの反論は即却下せず、審査対象とする。
- 実装AIが当初設計から大きく外れる場合は、事前に変更申請させる。
- 審査AIは実装しない。
- 審査AIは、逸脱の妥当性を判定する。
- 最終判断は、採用・条件付き採用・却下・要修正のように記録する。

## 3. 三者の役割

| 役割 | 目的 |
|---|---|
| 発注者 | 目的・制約・優先順位を決める |
| 実装AI | 設計・実装・修正を行う |
| 審査AI | 実装AIの提案や逸脱が妥当か審査する |

## 4. 実装AIの逸脱パターン

### 4.1 ユーザーの考慮不足を補っている

次のような場合、実装AIの反論や変更提案は有益な可能性があります。

- セキュリティリスクを指摘している。
- データ消失リスクを指摘している。
- 保守困難になる設計を避けようとしている。
- 実装方式に技術的な無理があることを指摘している。
- 仕様が曖昧で事故りそうな点を明確化しようとしている。

### 4.2 一般論に引っ張られている

次のような場合、当初目的やフェーズに合わない過剰な逸脱の可能性があります。

- 過剰なセキュリティ設計へ寄せている。
- 大規模アプリ前提の分割を提案している。
- テスト・設計・抽象化を優先しすぎている。
- 閉域・小規模・プロトタイプという前提を見失っている。

### 4.3 実装しやすい方向へ逃げている

次のような場合、プロトタイプ完成や利用者価値から逃げている可能性があります。

- UIを後回しにして内部ロジックばかり作る。
- 画面完成より設定ファイルやREADMEを増やす。
- プロトタイプ完成より基盤整備を進める。
- 統合作業を避けて小さなモジュール作成に逃げる。

## 5. 審査観点

| 観点 | 見る内容 |
|---|---|
| 目的適合性 | 当初目的に沿っているか |
| 制約適合性 | 技術制約・運用制約を守っているか |
| フェーズ適合性 | プロトタイプ段階で過剰設計していないか |
| UI/UX優先度 | 画面・操作性を後回しにしていないか |
| 安全性 | 最低限のリスク対策を無視していないか |
| 実装速度 | 小さな作業に逃げていないか |
| 保守性 | 将来の修正が極端に難しくならないか |
| 逸脱理由 | 設計変更に合理的な理由があるか |

## 6. 変更申請テンプレート

実装AIが当初設計から大きく外れる場合は、実装前に次の形式で変更申請を出させます。

```markdown
## 変更申請

- 変更対象:
- 当初方針:
- 変更後方針:
- 変更理由:
- 変更しない場合のリスク:
- 変更した場合のデメリット:
- ユーザー判断が必要か:
```

## 7. 判断ログテンプレート

審査結果とユーザーの最終判断は、次の形式で残します。

```markdown
## 判断ログ

- 日付:
- 論点:
- 実装AIの提案:
- 第三者レビューの判定:
- 最終判断:
- 理由:
- 実装AIへの指示:
```

## 8. 優先順位テンプレート

実装AIが一般論や過剰設計へ寄りすぎる場合は、次のように優先順位を明示してから再指示します。

```markdown
## 優先順位

1. 利用者が一連の操作を試せること
2. UI/UXが直感的であること
3. 現在の制約環境で動くこと
4. 実装が単純であること
5. 将来の拡張性
6. 厳密なアーキテクチャ設計
```

## 9. 判定区分

| 判定 | 意味 |
|---|---|
| 採用 | 実装AIの逸脱・反論に合理性があり、そのまま採用できる |
| 条件付き採用 | 一部条件を満たせば採用できる |
| 却下 | 当初目的・制約・フェーズに合わないため採用しない |
| 要修正 | 指摘の方向性は有益だが、提案内容を修正して再提示させる |

## 10. 注意事項

- このガイドは、実装AIの反論をすべて否定するためのものではない。
- ユーザー主権を前提にしつつ、ユーザー側の考慮不足も明確に扱う。
- 審査AIに実装を依頼しない。
- 審査結果だけで自動決定せず、最終判断はユーザーが行う。
- 判断に迷う場合は、変更申請・第三者レビュー・判断ログをセットで残す。
