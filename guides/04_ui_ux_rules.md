# 04_ui_ux_rules.md - 職員向け内部ツール UI/UX ルール

## 1. 目的

目的は、一般職員が説明を読み込まなくても迷わず作業を完了できることである。特定のレイアウトを揃えること自体を目的にしない。

## 2. 優先順位

機能や設定を増やす前に、次を減らす。

1. 利用者が見る情報量
2. 利用者が判断する回数
3. 操作の手数
4. 操作時の迷い

利用頻度と業務上の重要度が高い操作を目立たせる。既存機能へ自然に接続できる場合は、新画面、設定、説明、モードを増やさず統合する。

## 3. 操作と情報設計

- 利用者の業務の順序に沿って配置する。
- 必須入力と選択肢を最小限にし、妥当な初期値や自動判定を使う。
- 同じ内容を画面内で繰り返し説明しない。
- 主操作と補助操作の違いを明確にするが、ボタン数を機械的に制限しない。
- 結果と次の操作を同じ流れで確認できるようにする。
- 破壊的操作は誤操作を防げる確認を行う。

入力、実行、結果を順に示す構成、1画面構成、カード表現などは有効な場合の**例**であり、複数画面や既存画面への統合の方が迷いを減らすならそちらを選ぶ。

## 4. 表示文言とフィードバック

- 専門用語より利用者の業務用語を使う。
- エラーは「何が起きたか」と「次に何をするか」を短く示す。
- 例外名やスタックトレースは利用者向け表示にしない。
- 成功時は完了内容を示し、必要な場合だけ件数、出力先、次操作を示す。
- 入力値や個人情報をエラー文へ不必要に再表示しない。
- 色だけで状態を伝えず、文言や記号を併用する。

## 5. 視認性とアクセシビリティ

- 対象端末、対象ブラウザ、表示倍率で読みやすい文字と余白を確保する。
- 十分なコントラストと操作対象の大きさを確保する。
- キーボード操作、フォーカス順、ラベルを可能な範囲で確認する。
- 固定の文字サイズ、横幅、カード数は参考値にとどめ、実際の利用環境で判断する。

## 6. 実装方式別の例

### Web

静的な小規模ツールでは、概要、入力、主操作、結果を自然な順に置く構成が使いやすいことが多い。コピーやダウンロードを設ける場合は、成功・失敗と代替手段を必要に応じて示す。

### PowerShell

開始、進行、完了、注意、エラーを文言で区別し、対象と結果を短く示す。色なしでも判読できるようにする。

### C# GUI

自然なフォーカス順、具体的なラベル、必要に応じたファイル選択を用意する。常時ログ領域や多数の設定項目は、利用者に必要な場合だけ追加する。

## 7. 確認方法

- 初見の一般職員が目的と最初の操作を判断できるか。
- 完了まで不要な判断や往復がないか。
- 説明、設定、画面、モードを削除または統合できないか。
- 正常時・エラー時に次の操作が分かるか。
- 既存機能と用語・導線が矛盾しないか。
- 対象環境の画面サイズ・倍率で操作不能にならないか。
